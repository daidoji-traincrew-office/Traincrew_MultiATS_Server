# 連動盤クライアントのてこチャタリング 引き継ぎ

**起票日: 2026-09-08**
**対象リポジトリ: [TatehamaInterlockingConsole](https://github.com/daidoji-traincrew-office/TatehamaInterlockingConsole) (本リポジトリではない)**
**関連: 本リポジトリの `feature/broadcast-scheduler-snapshot`(配信系スケジューラ統合)**

## 1. 何が起きるか

連動盤でてこを操作すると、**新位置 → 旧位置 → 新位置** と一瞬戻ってから正しい位置に落ち着くことがある。
鍵てこでも同様。着点ボタンは後述のとおり経路が違うため症状が出にくい。

## 2. 原因はクライアント側にある

サーバー側の配信は正しい。原因はクライアントが
**「RPCの戻り値で楽観的に描画する」経路**と
**「配信で全リスト差し替えする」経路**の2つを持っていて、後者が前者を巻き戻すこと。

### 2-1. 楽観的描画(先に新位置を描く)

`TatehamaInterlockingConsole/Models/ServerCommunication.cs`

- `SendLeverEventDataRequestToServerAsync` (`:571`)
  → `SetPhysicalLeverData` の戻り値を `_dataManager.DataFromServer.PhysicalLevers` の該当要素へ反映 (`:585-591`)
  → `UpdateControl` (`:596`) で即描画
- `SendKeyLeverEventDataRequestToServerAsync` (`:619`) も同じ構造 (`:641-647`, `:652`)

### 2-2. 配信による全リスト差し替え(旧位置に巻き戻す)

`OnReceiveDataFromServer` (`:476`)

```csharp
foreach (var property in data.GetType().GetProperties())   // :494
{
    var newValue = property.GetValue(data);
    var oldValue = property.GetValue(_dataManager.DataFromServer);
    if (newValue != null && !newValue.Equals(oldValue))
    {
        property.SetValue(_dataManager.DataFromServer, newValue);   // :500
    }
}
```

`PhysicalLevers` は `List<LeverData>`。**`List<T>` は `Equals` を上書きしていない**ので
`newValue.Equals(oldValue)` は参照比較になり、配信のたびに必ず別インスタンス = 必ず `true` で差し替わる。
つまり「変更があれば更新」というコメントに反して、**毎回リストごと無条件に上書き**している。

差し替えに使われる配信データは、操作がDBにcommitされる前に取られたスナップショットでありうる。
その結果 2-1 で描いた新位置が旧位置で上書きされ、次のティック(250ms)で再び新位置になる。

```
t0  配信スナップショット取得(てこ=旧位置)
t1  操作者がてこを倒す → RPCが新位置を返す → 新位置を描画
t2  t0のスナップショットが到着 → PhysicalLevers をリストごと差し替え → 旧位置を描画  ← ここ
t3  次ティックの配信 → 新位置
```

### 2-3. サーバー側の変更が原因ではない

`feature/broadcast-scheduler-snapshot` で `SendData_Interlocking` の読み取り経路から
プロセス内mutexを撤去したが、**このチャタリングは撤去前から存在する**。

- 旧(mutex あり): 書き込みはmutex解放待ちなので、配信の読み取りが全部終わるまでcommitできない。
  配信中に操作されたら、その配信フレームは**必ず**古いてこ位置を運ぶ
- 新(mutex なし): 書き込みは即commitする。スナップショット取得より前に操作が入れば、
  **そのフレームに新位置が載る**。古くなるのは操作がスナップショットより後だった場合だけ

書き込みが読み取り完了を待たなくなった分、古いフレームが出る確率はむしろ下がる。
どちらの場合も古くなりうるのは「操作の瞬間に飛んでいた1フレームだけ」で、次ティックからは新位置。
したがってサーバー側でmutexを戻しても解決しない。

## 3. 直し方

### 3-1. 推奨: ローカル操作直後は配信の該当要素を採用しない

小さく収めるならこれ。`OnReceiveDataFromServer` の差し替えを
**リスト単位ではなく要素単位のマージ**にし、直近で自分が操作した要素だけ配信値を捨てる。

1. 操作した要素名と時刻を持つ辞書を用意する

```csharp
// ServerCommunication のフィールド
private readonly Dictionary<string, DateTime> _locallyOperatedAt = new();
private static readonly TimeSpan LocalOperationGuard = TimeSpan.FromMilliseconds(750); // 3ティック分
```

2. `SendLeverEventDataRequestToServerAsync` / `SendKeyLeverEventDataRequestToServerAsync` で
   楽観的描画したときに記録する

```csharp
lock (_locallyOperatedAt) { _locallyOperatedAt[data.Name] = DateTime.UtcNow; }
```

3. `OnReceiveDataFromServer` で `PhysicalLevers` / `PhysicalKeyLevers` だけリフレクション任せをやめ、
   ガード期間内の要素はローカル値を残す

```csharp
private void MergeLevers(List<DatabaseOperational.LeverData> incoming)
{
    var current = _dataManager.DataFromServer.PhysicalLevers;
    if (current == null) { _dataManager.DataFromServer.PhysicalLevers = incoming; return; }

    var now = DateTime.UtcNow;
    foreach (var received in incoming)
    {
        var local = current.FirstOrDefault(l => l.Name == received.Name);
        if (local == null) { current.Add(received); continue; }

        bool guarded;
        lock (_locallyOperatedAt)
        {
            guarded = _locallyOperatedAt.TryGetValue(received.Name, out var operatedAt)
                      && now - operatedAt < LocalOperationGuard;
        }
        if (guarded) { continue; }   // 自分の操作が配信に載るまで待つ

        local.State = received.State;
    }
}
```

`PhysicalKeyLevers` は `State` と `IsKeyInserted` の2つを反映すること。

4. `:494` のリフレクションループから `PhysicalLevers` / `PhysicalKeyLevers` を除外し、
   上記マージを呼ぶ

**ガード期間の考え方**: 配信周期は250ms。操作のcommit直後に飛んでいる古いフレームは最大1枚なので、
2〜3ティック分(500〜750ms)あれば足りる。長すぎるとサーバー側で操作が拒否された場合
(連動条件で倒せなかった等)に画面が実状態へ戻るのが遅れるので、伸ばしすぎないこと。

### 3-2. 代案: 楽観的描画をやめる

`:585-596` と `:641-652` の書き戻しを削除し、描画ソースを配信だけにする。
単調変化になるので振動は原理的に消える。実装は最小。
ただしてこを倒してから画面に反映されるまで最大250msの遅れが出る。
操作感が許容できるなら、こちらのほうが状態の持ち主が1つになり健全。

### 3-3. ついでに直すべき点

`:494` のリフレクションによる「変更があれば更新」は、
**すべての `List<T>` プロパティで参照比較になり常に差し替え**になっている。
`TrackCircuits` / `Points` / `Retsubans` / `Lamps` 等も同様なので、
このループ自体が意図どおり機能していない。要素単位マージへの置き換えを検討する価値がある。

## 4. 着点ボタンについて

`SendButtonEventDataRequestToServerAsync` (`:680`) は
`DataFromServer.PhysicalButtons` を書き換えず `_dataManager.PhysicalButtonOldList` を更新している
(`:692` 以降)。てこ・鍵てことは経路が違うため、同じ形のチャタリングにはならない。
ただし `PhysicalButtons` は `:494` のループで毎回差し替えられているので、
3-1 を入れる際は挙動を確認すること。

## 5. 検証方法

WPF (`net8.0-windows`) のため Linux ではビルド・実行できない。**Windows 環境が必要**。

1. `Docs/scripts/setup-console-dev.sh` でクライアントを clone し、
   リポジトリに含まれていない `ServerAddress.cs` を生成する(初回ビルドの詰まりどころ)

   > **罠**: クライアントの `.gitignore` が無視しているのは `Manager/ServerAddress.cs` と
   > `Properties/ServerAddress.cs` だけで、CI (`.github/workflows/build.yml:77`) が実際に書き出す
   > `TatehamaInterlockingConsole/ServerAddress.cs` は**無視されない**。放置すると untracked として現れ、
   > 接続先ごと誤コミットされうる。上記スクリプトは追跡対象の `.gitignore` を変更せず
   > `.git/info/exclude` に登録して回避している。クライアント側で `.gitignore` を直すのが本筋。
2. サーバーを起動する(本リポジトリ)

```bash
cd Database && docker compose up -d
cd .. && dotnet run --project Traincrew_MultiATS_Server.Crew
```

3. 連動盤を接続し、てこを繰り返し倒して巻き戻りが出ないことを目視確認する
4. 再現しにくい場合は配信周期を一時的に伸ばすと窓が広がって再現しやすい
   (`Traincrew_MultiATS_Server/Scheduler/BroadcastScheduler.cs` の `Interval`)

## 6. サーバー側の状況(参考)

- 配信は `BroadcastScheduler` に統合済み。1ティック=1トランザクション=1スナップショット
- 連動盤へは `ReceiveData` → `ReceiveSignalData` の順で逐次送信され、順序は保証される
  (`Traincrew_MultiATS_Server.IT/Hubs/BroadcastOrderingTest.cs` で検証)
- 書き込み経路6箇所はすべて単一文なので、読み手が半適用状態を観測することはない
- クライアント側の要件は「2つのハンドラを受信順に適用すること」のみ。現状これは満たされている
